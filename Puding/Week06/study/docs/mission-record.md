# 6주차 미션 기록

## 구현 과정

5주차 조회 코드를 별도 `Week06/study` 프로젝트로 확장하고 DB를 `umc_movie_week06`으로 분리했다. 회원가입 POST `/members`, 평점 POST `/members/{memberId}/ratings`, PATCH·DELETE `/members/{memberId}/ratings/{ratingId}`를 추가했다.

DTO의 Bean Validation으로 이메일·닉네임·비밀번호 및 평점 입력을 검사한다. movieId는 양수, score는 1~5 정수, comment는 선택 입력이며 500자 이하다. 서비스는 회원 존재, 중복, 평점 소유자를 검사한다. 회원가입은 BCrypt cost10으로 해시하고 응답에는 memberId·email·nickname만 담는다. UTF-8 비밀번호가 72바이트를 넘으면 400으로 거절한다.

쓰기 성공과 실패는 `isSuccess/code/message/result` 구조를 쓴다. 생성201, 수정200, 삭제204를 반환한다. 204에는 본문을 넣지 않는다. 기존 GET 성공 응답은 `{available}` 또는 평점 배열을 유지한다.

중복 이메일은 MEMBER4091, 닉네임은 MEMBER4092, 평점은 RATING4091로 구분한다. 없는 회원·평점은404, 타인 평점 변경은403이다. UNIQUE 제약 이름에 따라 DB 저장 단계 중복도 같은409 코드로 변환한다. 알려지지 않은 무결성 오류를 중복으로 간주하지 않는다.

## 실제 검증

2026-11-03 Java21·Spring Boot3.5.0·MySQL8.4.11에서 통합 테스트 **16개**, 실행 중인 서버 HTTP 요청 **27건**이 통과했다. 비밀번호 해시 저장·응답 제외, 검증400, 중복409, 소유권403, 존재 여부404, 등록·수정·삭제와 조회, 204 빈 본문, CORS 사전 요청을 확인했다. 원문 결과는 `../../results/integration-verification.json`과 `../../results/http-verification.json`에 있다.

DB UNIQUE 검증은 `@MockitoSpyBean`으로 특정 이메일의 사전 중복 검사만 통과시키고 실제 MySQL INSERT를 수행했다. MySQL1062·SQLState23000·`uk_member_email` 위반이 발생했고 HTTP409 MEMBER4091을 확인했다. 이는 실제 DB 제약 경로를 검증한 것으로, 동시 HTTP 요청을 실행한 실험은 아니다. 일반 테스트 데이터는 롤백했고 이 별도 테스트의 회원은 finally에서 삭제했다.

HTTP 검증은 합성 회원2명과 캡처용 평점을 남겼다. 현재 예시 ID는 결과 JSON의 `captureDemo`를 확인한다. ID는 재실행마다 달라진다. Postman16개 요청은 Import용으로 만들었으며 Postman 앱 실행·화면 캡처는 아직 수행하지 않았다.

## 트러블슈팅 및 설계 점검

**이슈 — 사전 검사만으로 중복 저장을 막을 수 있는가?**

사전 조회와 저장 사이에는 다른 요청이 들어올 수 있다. 서비스 중복 검사와 DB UNIQUE를 함께 두고 전역 예외 처리에서 제약 이름을 같은 오류 코드로 변환했다. 사전 검사를 우회한 통합 테스트에서도 실제 DB가 거절하고409를 반환했다.

**점검 — 정수 필드에 소수 입력이 들어오는 경우**

Jackson의 소수→정수 변환을 막기 위해 `accept-float-as-int:false`를 설정했다. score1.5와 movieId550.5가400으로 거절되는 테스트가 통과했다. 설정 전 실제 런타임 장애가 발생한 것으로 기록하지 않는다.

**점검 — 공통 응답과 DELETE204**

공통 JSON을 모든 성공에 붙이면204의 빈 본문 규칙과 충돌한다. DELETE는 `ResponseEntity.noContent()`로 반환하고, 실제 HTTP 검증에서 bodyBytes0과 삭제 후 빈 배열을 확인했다.

## 작업 회고

저장 API는 입력 형식만 맞는다고 성공하는 것이 아니라 회원 존재·소유권·중복과 DB 제약을 단계별로 확인해야 한다는 점을 정리했다. 서비스의 친절한 오류와 DB의 최종 무결성 보장이 서로 다른 역할을 맡는다는 점을 DB 제약 경로 테스트로 확인했다.

응답에서 password를 빼는 것과 DB에 해시로 저장하는 것은 각각 검증할 항목이었다. 정상 CRUD뿐 아니라 잘못된 입력, 다른 회원의 요청, 삭제된 데이터와204의 빈 본문을 함께 검증하니 응답 규칙도 명확해졌다.

경로 memberId 비교는 현재 실습의 소유자 확인이며 로그인 인증은 아직 구현하지 않았다. 다음에는 토큰에서 현재 회원을 얻는 방식과 실제 동시 요청 상황을 더 학습할 계획이다. 직접 촬영·첨부와 Postman 앱 실행은 남아 있다.
